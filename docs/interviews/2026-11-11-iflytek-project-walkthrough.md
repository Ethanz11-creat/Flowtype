# 科大讯飞面试：FlowType 项目讲述与追问

目标岗位：AI研究算法工程师–语音大模型方向（J13388）。这次准备的目标是理解一条可运行的语音大模型应用链路，用固定数据验证工程取舍。重点连接自己熟悉的 LLM/PyTorch 与新接触的语音任务。岗位原始要求见 [需求记录](2026-11-11-iflytek-speech-llm-requirements.md)。

先读实际证据再背数字：`build/interview-bench/reports/report.md` 与仓库 `docs/evidence/iflytek-interview/`。本文件的实验表会在本批次结束后冻结。训练、量化转换和模型预训练均来自上游；本轮工作是推理适配、因果分段、纠错对照与评测工具。AI辅助实现的代码，需要能独立解释调用、张量、状态机和失败路径。

## 30 秒介绍

我做了一个 macOS 语音输入工具 FlowType，并围绕它搭了一套可复现的语音评测工具。我关注三个实际问题：不同部署模型的识别与资源取舍，VAD 分段对等待和识别的影响，以及 LLM 利用候选词纠错时的收益与误改。实现上用 Swift/MLX 跑 Qwen，用 PyTorch 跑 Whisper 和 Silero；固定数据、参数与失败策略，分别保存识别文本、事件和评分，能追溯每个结论的来源。

## 3 分钟介绍

FlowType 的产品链路是录音、ASR、可选文字处理，再向目标应用发送文本。为了让面试讨论有真实证据，我把实验与客户端隔离，冻结了 ASCEND 的 1,130 条音频，其中 clean-reference 1,067 条、中英混说 191 条；另用 200 条 LibriSpeech 做候选词纠错试验。输入、参考、词表分别保存，避免把答案交给模型。

第一部分比较部署方案。我对 Qwen3-ASR 的 1.7B、0.6B MLX 4bit，以及 Whisper base 的 PyTorch CPU FP32，使用同一音频、各自固定解码参数。每个模型独立进程加载，三条预热后重跑完整数据，分别记录加载、推理、RTF 和进程 RSS。后端与硬件路径不同，所以这些结果帮助选择实际部署方案；不能把速度差异全归因于参数量或架构。

第二部分是 VAD。我实现了 32ms 帧的因果分段，带滞回阈值、前后缓冲、最长段限制和有界队列。ASR 使用独立串行消费线程，慢推理不会暂停音频时钟。短词候选保留给 ASR，队列过载明确失败，不悄悄丢段。使用真人片段构造固定会话，比较整段、固定五秒和 VAD；缺少真人试听边界时，端点延迟保持空值，先报告识别和首段返回。

第三部分是上下文纠错。我固定一个 LLM 服务和提示，在英语上比较无词表、正确候选表和错配候选表，在中英混说上比较无词表和产品既有技术词表。词表包含干扰项，LLM 只拿到原 ASR 文本与该条件词表。API失败保留原文，全样本计分，同时检查 B-WER/U-WER、原本正确句的误改与网络耗时。它让我能解释收益来自哪些词，也能展示错配上下文诱导替换的风险。

最后，统一 CLI 检查 ID、哈希、分母、失败和人工待验证项。我的重点是把“能跑”变成“能复现、能解释、知道边界”。下一步会优先完成真人边界和客户端演示，而不是继续堆模型或对同一批错误反复调提示。

## 追问与回答要点

1. **Qwen 与 Whisper 的区别怎么讲？** 先分清具体 checkpoint、架构和部署：本实验Qwen3-ASR通过Swift/MLX，Whisper base通过PyTorch CPU。查上游模型结构再讲编码器、文本解码器和训练任务，不能把所有差异归结为“LLM更聪明”。这里没有训练或声学结构消融。
2. **为什么量化到4bit不一定占原来四分之一内存？** 部分权重保持较高精度；还有scale/bias、激活、KV cache、临时张量、运行时和Metal缓存。文件大小、RSS与实际GPU分配是不同量。本轮只报告进程RSS覆盖范围。
3. **PyTorch输入张量是什么？** SoundFile读16kHz单声道float32；Whisper内部做log-Mel和特征编码，Silero接收512样本窗口。核对采样率、维度、有限值与模型期望，不能只改采样率标签。
4. **`eval()`、`no_grad()`、`inference_mode()`区别？** eval影响dropout/batchnorm等模块行为；no_grad关闭autograd图记录；inference_mode还减少版本计数等开销、限制更强。Silero显式eval/inference_mode，Whisper上游解码函数带no_grad；不能宣称做了这些模式的性能消融。
5. **VAD为什么用0.5/0.35两个阈值？** onset和offset形成滞回，减少边界抖动；静音持续时间、短语音确认、padding是不同机制。这里固定参数，在开发集并列展示300/600/900；评测固定600，不按最好成绩选。
6. **为什么不能直接切掉短于96ms的段？** VAD概率和持续时间不完美，极短词、轻声会被误伤。此实现保留有语音概率的未确认候选，EOS仍送ASR，代价是可能多一些噪声推理。
7. **“实时”和“流式”具体指什么？** 本原型按单调时钟每32ms投递音频，ASR对完成的片段做批推理，文字按段增量出现。它没有证明模型逐token流式生成，更没有证明客户端已经逐段落字。
8. **慢ASR怎么处理？** 采集/VAD继续按时钟推进，串行worker消费有界队列；记录入队、等待、返回。四个待处理片段之外明确会话失败，避免无限内存和隐蔽丢音；当前没有自适应降级或跨模型切换。
9. **取消时为什么不能马上关模型？** 底层计算可能不支持中断。先停止后续投递，取消待处理任务，等待在途计算退出，再由调用者关闭worker。这样不把后台仍在跑的模型当作已清理。
10. **MER为什么不用纯中文CER或英文WER？** 中英混说统一为汉字/字母单词/数字串的混合单元，NFKC+casefold，微平均总编辑数/总参考单元。明确这是一套冻结自定义口径，不能和其他论文的未知规范直接比。
11. **为什么63条UNK参考不放主分母？** 标注含未知片段，不能公平定义对应词数。仍保留全部1130条预测与UNK诊断，clean1067单列；不能删掉难样本后称完整官方validation成绩。
12. **B-WER与U-WER怎么来的？** 官方评分器用第三列真实稀有词划分B/U、加权对齐。模型提示只拿第四列完整候选表（含干扰项）；把第三列给LLM会引入答案信息。逐句误改诊断用单位代价编辑距离，应与官方聚合口径区分。
13. **错配词表为什么允许包含正确词？** 对照按ID循环换整张候选表，不查答案删重合词，保留实验规则。它是错配上下文，不保证完全无关；事后报告覆盖，不能靠参考造“完美负例”。
14. **如何证明纠错没有编造？** 没有绝对保证。看总体WER/B/U、原本正确句误改、数词/否定/专名案例和fallback，并展示负例。当前没有置信度校准、声学复核或n-best约束，不能凭提示词声称安全。
15. **网络失败怎么评分？** ASR失败按空假设计漏字；LLM失败使用原始ASR作为有效管线输出，同时单独计fallback和网络耗时。两种失败策略服务不同阶段，不能悄悄丢样本、换供应商或无限重试。
16. **数据是否泄漏/是否是盲测？** 推理字段白名单避免参考直接进入请求，但既有基线和pilot已看过、LLM预训练数据未知，这只是固定公开语料的探索性评测。不能宣称独立盲测或泛化到真实技术会议。
17. **端点延迟怎么算，负数是什么意思？** 使用真实单调时钟记录的切段事件时间，减人工语音结束样本换算的秒数；另存decision_sample与speech_end_sample之差，便于区分帧量化与执行滞后。过早切段保留负值。最终文本返回减语音结束包含等待与推理。自动静音拼接边界不能冒充真实语音端点。
18. **研究原型和产品还差什么？** 本轮没有把VAD原型接进产品默认链路。产品还需真实麦克风、跨应用落字、取消和设备变更、权限、剪贴板保护与实际云端弱网覆盖；现有历史实现和本轮算法实测分别陈述。发送事件不等于确认落字。

## 演示与复练

- 先运行 `report`/`verify` 打开真实表格，选一条提升、一条误改解释前后文本；说明选例规则，不把例子当总体分布。
- 打开eval策略目录HTML，播放构造音频，观察逐段结果与队列事件；主动说明它不是麦克风录屏和token streaming。
- 在空白TextEdit使用现有客户端做短句、混说、术语三次真实录音，逐次人工核对实际文字。此项在操作发生前保持pending。
- 能自己画出：PCM→VAD状态机→有界队列→常驻ASR→原始文本→可选LLM→评分。顺着一次失败说明谁决定回退、哪些耗时计在哪里。
- 面试前一天冻结新增方法，最后一天读代码、跑命令和讲述。讲自己能解释的实现；如果具体模型结构或PyTorch细节尚未读懂，应说明并现场追踪代码。
