# M3 执行裁定与代价

按执行顺序归档全部 `Ruling:`；英文原文保留在同目录 a/progress.md 与 b/progress.md。

1. A3 中间发布构建/GUI 批次合并到 B 完成后的最终 M3 产物；A 源码阶段审查保留。原因：当前无 GUI 工具，中间打包不会增加真机证据。代价：A 独立打包问题延后到最终打包才发现。
2. ASRStage 无已有 CompletionBudget 时在 preflight 前创建；已有预算保留。原因：遵守同一个停止后 20s 预算，解决计划中先后顺序矛盾。代价：直接调用者的识别可用时间扣除预检耗时。
3. 原构建脚本的可选 Python import 探针用仅返回失败的 shell 函数屏蔽，仍由原脚本复制已存在的 Metal 缓存资源。原因：遵守不运行 Python、不安装依赖。代价：若只有 Python 安装路径可发现资源，打包会失败；本机已有缓存路径。
4. B2 完整自测启动后仅加强旧结果测试的完成屏障：保留当轮完整生产验证，对加强测试再跑 focused/build。原因：生产代码未变，不重复全套。代价：仅完整顺序才出现的测试 harness 交互可能漏检。当时版本差异已保留；其后最终修复版已重新完整通过 4124/0，最终屏障亦在完整 suite 中。
5. F2 取消处理从“已有 uncertain 才保存”改为“仍持有当前会话时，按真实事件证据同步建立 uncertain 再保存”；保留一次历史与迟到结果限制。原因：同时满足已发键取消可恢复、旧会话不能发布。代价：已完整发送但尚未完成保存的取消也会保守标为 uncertain；只有临时写板不满足条件。

最终审查搁置的行为均依明确范围处置：人声/噪声分类不属于能量检查，真实校准仍必做；实时零上传/计费不在停止后 gate 承诺内；AX 插入确认属后续范围，现有文案保持未确认语义；当前产物 GUI/服务/外设表现须真实验收，保持 Pending；最终打包按源码关口后执行。这些不是取消验收要求。
